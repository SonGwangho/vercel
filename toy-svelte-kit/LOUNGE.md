# 모닥불 라운지

## 화면과 조작

- `/lounge`: 닉네임과 캠핑장을 고르고 입장한다. 미리보기의 꾸미기 버튼에서 외형을 바꾼 뒤 완료하면 입장 폼으로 돌아온다. 닉네임은 정규화 후 1~6자이며 같은 캠핑장 안에서 중복할 수 없다. 이름표는 전체 이름을 표시한다.
- `/lounge/1`~`/lounge/3`: 모닥불이 켜진 숲속 캠핑장. 텐트, 등불, 통나무 의자, 피크닉 테이블을 배치했다. 카메라는 내 캐릭터를 따라가며 휠과 +/− 버튼으로 확대할 수 있다. 상단 텐트 버튼은 모닥불 앞으로 이동한다.
- 좌클릭 또는 터치로 이동한다. 모닥불·텐트·테이블은 경로를 돌아간다. 경로 계산은 서버와 클라이언트가 공유한다.
- 캐릭터와 바닥 음식, 호수를 우클릭하면 행동 메뉴가 열린다. Space도 같은 메뉴를 열며 마우스로 가리킨 대상, 주변에서 가장 가까운 대상, 내 캐릭터 순으로 선택한다. 주변 선택 범위는 캐릭터 190, 음식 108 월드 단위이며 호수는 낚시 가능한 물가에서 선택된다. 낚시 중 Space는 낚아채기를 유지하고 입력창·메뉴·채팅 기록·조작 안내를 사용하는 중에는 별도 상호작용을 열지 않는다. 키를 길게 눌러도 중복 요청하지 않는다. 터치는 450ms 길게 누른다. 이름표에서 Enter 또는 ContextMenu 키를 눌러도 된다.
- 내 캐릭터의 **혼자 놀기**에서 뻐큐 날리기·웃기·춤추기·인사·메롱하기를 선택한다. 손가락 모양, 웃는 눈과 입, 춤 동작, 머리에 올린 손, 윙크와 혀로 구분하며 다른 참가자에게도 같은 행동 상태를 전송한다. 상대의 동의는 필요하지 않다.
- 혼자 하는 표현은 1.6~4.8초 뒤 끝나고, 진행 표시나 내 캐릭터 메뉴의 **그만하기**로 일찍 멈출 수 있다. 행동·기절·동의 대기 중에는 새 표현을 시작할 수 없고, 표현 중 다른 상호작용도 차단한다. 손의 음식은 소모하지 않고 가방에 넣는다.
- 음식 줍기는 가방에 넣는 동작이다. 내 캐릭터 메뉴에서 **손에 들기**를 선택하고, 이후 별도로 **먹기**를 선택한다. 손에 든 음식은 3D 캐릭터에 표시되며 게임 화면의 작은 음식 버튼에서도 먹거나 다시 가방에 넣을 수 있다.
- 기록 버튼으로 게임 안의 채팅 기록 패널을 열고 닫는다. 최근 30분 중 최대 100개를 표시하며 채널이 비면 초기화한다. 안 읽은 대화 수, 작성자와 시각을 표시한다. 과거 내용을 읽는 동안 새 메시지가 와도 스크롤을 유지하며 새 메시지 보기로 맨 아래로 이동한다. 입력창과 함께 열어둘 수 있다. 기록은 영구 보관하지 않는다.
- 가방 전체·참여자 목록을 별도 화면으로 펼치지 않는다. 내 캐릭터 버튼은 우클릭과 같은 메뉴를 연다.
- Enter 또는 한마디 버튼으로 최대 60자의 대화를 보낸다. 말풍선은 실제 머리 위에 고정하고 내용이 길어지면 위로 늘어난다. 겹치면 최신 메시지의 z-index가 더 높다. 이름표의 겹침 회피 배치에는 영향을 받지 않으며 내부 스크롤과 말줄임을 사용하지 않는다. 최근 대화는 화면 읽기 프로그램에도 알린다.
- 먼 대상의 줍기나 상호작용을 선택하면 가까이 이동한 뒤 실행한다. 새 이동·Escape·대상 이탈은 예약을 취소한다.
- 악수·포옹·음식 선물은 상대 수락이 필요하다. 수락 시 서버가 모델 팔 길이에 맞춰 두 사람 사이의 간격과 시작 시각을 정한다. 장애물 주변에 공간을 확보하지 못하면 행동을 시작하지 않는다. 동의 대기 중에는 양쪽에 추가 요청을 보낼 수 없다. 12초 후 요청이 만료된다.
- 펀치는 상대 동의 없이 실행하며 1.5초 기절한다. 기절 중 이동·채팅·음식 사용·상호작용은 차단된다. 이미 행동하거나 요청을 기다리는 대상에게 중첩 실행할 수 없다.
- 펀치를 맞으면 손에 들고 있던 음식 한 개만 가방에서 빠져 바닥에 떨어진다. 공격 반대쪽의 이동 가능한 지점으로 튕겨 나가며 누구나 다시 주울 수 있다. 음식 ID는 유지하므로 복제되지 않는다. 손에 음식이 없으면 가방의 다른 음식에는 영향이 없다.
- 먹기는 손을 입으로 올리는 동작, 줄어드는 음식, 부스러기와 효과음을 사용한다. 움직임 줄이기 설정에서는 장식 입자와 모닥불의 흔들림을 줄인다.

## 호수와 낚시

- 서쪽 호수를 우클릭한 뒤 낚시하기를 고르거나 상단의 낚시 버튼을 누른다. 물가에서 멀면 먼저 접근하고, 물 안으로 들어가는 이동 경로는 우회한다.
- 낚싯대를 뒤로 당겼다가 앞으로 던지는 0.9초 동작에 맞춰 찌가 물에 떨어진다. 찌가 내려앉은 뒤 12초 안에 좌우로 움직이는 바늘이 성공 구간에 있을 때 좌클릭한다. 게이지 버튼은 누르는 순간 판정하며, 게임 바닥 좌클릭과 Space도 지원한다. Escape 또는 닫기 버튼으로 취소한다.
- 서버가 성공 구간과 시작 시각을 정하고 클릭 시각을 확인한다. 통신 지연 보정은 최대 250ms다. 한 시도에서 한 번만 포획할 수 있다.
- 성공하면 1.15초 동안 낚싯대를 들어 당기고 물고기가 물에서 손까지 날아온다. 이 동작을 마친 뒤 물고기를 양손에 들고 화면 정면을 바라본다. 오른쪽 팝업에서 가방에 넣기 또는 버리기를 선택할 때까지 이동과 추가 행동을 잠근다. 보관 선택이 완료된 물고기는 채널 세션 안에서 최대 10마리까지 보관하며 내 캐릭터 메뉴에서 손에 들기로 다시 꺼내거나 놓아준다. 복귀할 때 유지되는 세션의 복구 상태에 포함되며 퇴장 이후 영구 수집 기록은 저장하지 않는다.
- 물고기를 손에 들고 있는 동안 이름·등급·크기를 캐릭터 옆에 상시 표시하여 다른 참가자도 볼 수 있다. 포획 모션과 손에 든 상태 모두 같은 길이 기준을 쓰며, 작은 물고기도 알아볼 수 있는 최소 표시 크기를 두고 1m까지는 선형으로 커진다. 그 이상은 증가 폭을 완만하게 줄여 월드 길이 2.7 단위로 제한한다. 몸통·지느러미·꼬리·눈·무늬를 어종마다 구분하며, 종류별 모델은 하나의 메시로 합쳐 재사용한다. 큰 물고기는 몸에서 앞으로 띄운다. 좁은 화면에서는 성공 직후 카메라를 조금 옮겨 캐릭터와 오른쪽 선택 팝업의 자리를 확보한다.

| 물고기 | 등급 | 성공 후 등장 비율 | 길이 |
| --- | --- | --- | --- |
| 잉어 | C | 54.9% | 22–62cm |
| 광어 | B | 25% | 35–95cm |
| 빨간도미 | A | 13% | 28–74cm |
| 장어 | S | 6% | 46–128cm |
| 고래 | SS | 1% | 3.8–11m |
| 상어 | SSS | 0.1% | 1.6–5m |

형태 참고: [잉어 — FWC](https://myfwc.com/wildlifehabitats/profiles/freshwater/common-carp/), [광어류 — NOAA](https://www.fisheries.noaa.gov/species/summer-flounder), [빨간도미 — FWC](https://myfwc.com/wildlifehabitats/profiles/saltwater/snapper/red-snapper/), [장어류 — FWC](https://myfwc.com/wildlifehabitats/profiles/freshwater/american-eel/), [고래류 — NOAA](https://www.fisheries.noaa.gov/species/humpback-whale), [상어 — NOAA](https://www.fisheries.noaa.gov/species/white-shark/science). 세부 모델은 Three.js의 메시·곡선과 `BufferGeometryUtils`를 사용해 코드에서 생성하며 외부 모델 파일은 추가하지 않는다.

종류·크기·등장 비율과 게이지 설정은 `src/lib/assets/data/lounge/fishing.json`에서 관리한다.

## 기본값과 외형

`src/lib/assets/data/lounge/config.json`과 `campground.json`에서 관리한다.

혼자 하는 표현의 목록·이름·길이는 `emotes.json`에서 관리하며 클라이언트 예측과 서버가 같은 길이를 사용한다. 움직임 줄이기 설정에서는 표현의 반복 흔들림과 장식 입자를 줄이고 자세와 표정은 유지한다.

- 캠핑장 3개, 각각 최대 16명.
- 논리 공간 2400×1800. 이동 경로가 300 단위보다 짧으면 초당 155 단위로 걷고, 그 이상이면 초당 300 단위로 달린다.
- 음식은 삼각김밥·닭다리·피자. 채널 전체에서 1분마다 무작위 접속자 근처에 하나 생성한다. 첫 입장 때 즉시 만들거나 놓친 주기를 한꺼번에 생성하지 않는다.
- 주기적으로 생기는 바닥 음식은 최대 2개, 유지 시간 2분. 펀치로 떨어진 음식은 이 개수 제한과 별도로 2분간 유지한다. 가방 용량은 5개다. 먹기에는 별도의 능력치 효과가 없다.
- 실제 입력 없이 5분이 지나면 퇴장한다. 연결 확인용 ping/pong과 서버 heartbeat는 활동으로 인정하지 않는다. 네트워크가 끊긴 접속은 재연결을 위해 최대 45초 유지한다.
- 머리 8종, 긴팔·반팔·나시·후드티, 긴바지·반바지·긴치마·짧은 치마를 지원한다. 머리색 10개, 상의색 12개, 바지색·치마색 각 10개를 제공한다. 외형 목록은 `appearance.json`에서 관리한다.
- 프로필과 효과음 설정은 기존 IndexedDB `Storage`를 사용한다. 외형 값은 서버에서 허용 목록으로 정규화한다.

## 실시간 연결

브라우저의 게임 상태 수신은 HTTP long polling 대신 WebSocket을 사용한다.

1. `GET /api/lounge/ticket`은 기존 SvelteKit 훅을 거쳐 60초짜리 서명 티켓을 발급한다.
2. 브라우저가 같은 출처의 `/api/lounge-socket`으로 연결한다. 서버는 Origin과 티켓 서명을 확인한다.
3. 입장·복귀·이동·대화·음식·동의를 같은 연결로 전달한다. 서버는 바뀐 플레이어와 목록만 클라이언트에 전송한다. 대화는 추가·만료된 메시지 ID를 구분해 기록 전체를 매번 전송하지 않는다.
4. 채널별 메모리 권한 서버에서 이동·음식 소유·동의·기절을 판정한다. 해당 인스턴스에 연결된 사용자에게는 DB 저장 완료를 기다리지 않고 바로 반영한다.
5. 여러 함수 인스턴스가 생기면 Neon의 세션 advisory lock으로 채널 권한 서버를 하나만 정한다. LISTEN/NOTIFY로 명령과 상태를 중계하고 상태 전송은 최신 값으로 합친다. 이 경우 인스턴스 간 전달에는 Neon 왕복 시간이 남는다.
6. 복구 상태는 10초 간격과 연결 인계 때 checkpoint에 기록한다. 매 이동마다 행을 읽고 갱신하는 방식은 사용하지 않는다. checkpoint 저장 완료는 일반 입력 응답을 막지 않는다.

복구용 `lounge_realtime_checkpoints` 테이블은 첫 연결에서 생성한다. 기존 `DATABASE_URL` 계정에 테이블 생성·조회·쓰기 권한이 필요하다. LISTEN과 세션 잠금을 유지하도록 Neon pooler 호스트의 `-pooler`를 제거한 direct 연결을 사용한다. 공개 메시지에는 세션 토큰 해시와 접속 관리 필드를 넣지 않는다.

새 외부 서버 계정이나 SSH 설정은 요구하지 않는다. `DATABASE_URL`은 기존 Vercel 환경 변수를 사용하며 티켓 서명에도 이용한다. 별도의 서명 키를 분리할 경우에만 `LOUNGE_SOCKET_SECRET`을 설정한다.

## 배포 구성

[Vercel WebSocket Functions](https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections)의 Node HTTP server + ws 방식을 사용한다.

- `src/lib/server/lounge/entry.ts`: WebSocket 서버 진입점.
- `scripts/lounge-adapter.mjs`: 기존 SvelteKit 어댑터가 끝난 뒤 실시간 함수를 Build Output API의 `.vercel/output/functions/lounge-realtime.func`로 패키징한다. `/api/lounge-socket` 한 경로만 해당 함수로 연결한다.
- 루트 `api/` 디렉터리로 함수를 추가하지 않는다. [SvelteKit의 기존 `/api/*` 경로가 가려지는 충돌](https://svelte.dev/docs/kit/adapter-vercel#Notes-Vercel-functions)을 피하기 위한 구성이다.
- 게임 함수의 배포 지역은 `icn1`, 실행 한도는 300초다. 일반 웹/API 함수의 지역 설정은 유지한다. `vercel.json`에서 Fluid Compute를 활성화한다.
- 240~255초마다 연결을 교체하고 기존 세션으로 자동 복귀한다. 복귀 중에는 새로운 행동을 잠시 막으며 소비성 행동을 무조건 재전송하지 않는다.
- `vite.config.ts`는 개발 서버에도 동일한 WebSocket 핸들러를 연결한다. 개발 시에도 기존 `DATABASE_URL`이 필요하다.

기존 HTTP lounge API는 이전 클라이언트 호환 코드로 남아 있다. 새 게임 클라이언트는 해당 상태 조회·명령 경로를 사용하지 않으며, 이전 DB 방 상태와 새 메모리 방 상태는 서로 섞지 않는다. 배포 버전별 실시간 범위도 분리한다.

## 렌더링과 반응

- Three.js 렌더러를 동적으로 불러온다. 캐릭터와 미리보기는 같은 모델을 공유한다.
- 캐릭터 원본은 PolyOne Studio의 [Free Pack - Chibi Base Mesh (Rigged)](https://sketchfab.com/3d-models/free-pack-chibi-base-mesh-rigged-fed4fb329f224f1594f631eae8d2626b)이다. 공개 원본에는 CC Attribution이 표시되어 있다. 라운지에서는 관절의 기본 자세를 복원한 모델에 헤어·의상·표정을 추가한다.
- 첨부 GLB의 몸체 스킨은 24개 관절을 참조하고, 눈 스킨은 같은 머리 관절을 참조한다. 골반에서 척추·목·머리와 양쪽 다리로 분기하며, 가슴에서 어깨·팔꿈치·손목·손가락 그룹으로 이어진다. 변환본의 관절 노드에 빠진 기본 위치와 회전은 역바인드 행렬로 복원한다. `scripts/import-lounge-chibi.py <첨부 GLB 경로>`로 라운지용 GLB를 생성한다.
- `src/lib/lounge/avatar.ts`는 Three.js에서 대기·걷기·달리기와 각 행동을 계산한다. 이동 속도에 맞춰 보폭과 주기를 보간하고, 팔과 다리는 두 관절을 풀어 손과 발을 목표 위치로 움직인다. 악수는 공유 접점과 시작 시각을 사용하고, 포옹은 상대 쪽 양옆에 팔을 내밀며, 음식 건네기는 같은 시각에 표시할 손을 바꾼다.
- 나무·풀·돌·텐트·가구는 지오메트리와 재질별 instanced mesh로 묶는다. 모닥불과 불씨는 고정 개수의 인스턴스로 움직인다. 그림자 맵·후처리·물리 엔진은 사용하지 않는다.
- 캐릭터 외형 재질은 외형이 바뀔 때만 갱신한다. DPR 상한은 1.5, 장식 파티클 상한은 120개다. 원본 모델은 서버에 포함하며 실행 중 외부 에셋 사이트에 접속하지 않는다.
- 애니메이션과 이름표 좌표는 Svelte 반응형 상태를 매 프레임 변경하지 않고 직접 갱신한다. 이름·말풍선 배치는 최대 100ms에 한 번 계산한다. 이동 중 최대 60fps, 정지 중 최대 24fps로 제한한다. 측정된 성능 수치가 아니다.
- 내 이동은 클릭 즉시 예측한다. 목적지 전송은 40ms 안에서 최신 클릭으로 합치고 이전 이동 응답을 기다리지 않는다. 음식 들기·먹기·줍기·펀치에도 즉시 피드백을 준다.
- 다른 사용자는 수신한 경로를 현재 서버 시각으로 보간한다. 별도 프레임 지연 버퍼는 두지 않는다. ping 왕복 시간을 이용해 시계를 보정한다.
- 화면이 숨겨지면 렌더링을 멈춘다. 연결은 유지하되 실제 활동이 없으면 5분 규칙대로 퇴장한다. 퇴장 시 관찰자·이벤트·오디오·GPU 리소스를 해제한다.
- Taste Skill과 Impeccable의 화면 위계·가독성·상태 표현 원칙, 프로젝트 `DESIGN.md`의 한글 폰트·블루 컨트롤·라이트/다크 토큰을 적용한다. 캠핑장 도형은 코드로 구성한다.

## 한계와 검증 범위

네트워크와 여러 인스턴스 사이의 중계 지연은 남는다. 갑작스러운 모든 인스턴스 종료에서는 마지막 checkpoint 이후의 일부 상태가 유실될 수 있고, 새 배포나 만료된 세션에서는 다시 입장해야 한다. 10초 checkpoint는 게임 기록을 영구 보존하는 기능이 아니다.

사용자 요청에 따라 빌드·타입 검사·자동 테스트·브라우저 실행·다중 사용자 검증·성능 측정·실제 DB 접속·배포 확인을 실행하지 않았다. 배포에 필요한 코드를 작성한 상태이며 실서비스에서 작동을 확인한 결과는 아니다.
